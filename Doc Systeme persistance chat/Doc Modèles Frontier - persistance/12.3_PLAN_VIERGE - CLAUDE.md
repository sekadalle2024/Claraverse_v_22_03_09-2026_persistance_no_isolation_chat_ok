\## 0. CE QUE J'AI TROUVÉ EN LISANT LE CODE (et qui change le diagnostic)



Les documents 02/03 posent une hypothèse unique : \*« ClaraAssistant.tsx n'appelle jamais `restoreTablesChronologically()`, donc rien n'est restauré »\* (confiance 85%).



En inspectant `conso.js`, `flowiseTableBridge.ts` et `flowiseTableService.ts`, je constate qu'il existe en réalité \*\*deux systèmes de persistance complètement indépendants\*\*, et que le système suspecté (flowiseTableBridge + IndexedDB) \*\*n'est probablement pas celui qui gère Table\_Conso / Resultat / Modelised\_table\*\* — celui-là a son propre mécanisme, séparé et déjà "auto-restaurant". C'est là que se trouve le vrai problème.

`conso.js` dispatch uniquement des événements `claraverse:table:updated`, `claraverse:table:created`, `claraverse:consolidation:complete`. Aucun `flowise:table:save:request` ni `flowise:table:integrated`.



\### Preuve 2 — flowiseTableBridge.ts n'écoute pas ces événements



```typescript

document.addEventListener('flowise:table:integrated', ...);

document.addEventListener('flowise:table:save:request', ...);
```

Le Bridge écoute `claraverse:session:changed` mais \*\*pas\*\* `claraverse:table:updated/created/consolidation:complete`. Donc \*\*le flux Phase 1 décrit dans le doc 02 (conso.js → index.html → Bridge → IndexedDB) ne concerne pas Table\_Conso/Resultat/Modelised\_table\*\*, sauf si `index.html` (non fourni) fait la traduction entre les deux familles d'événements — ce qui n'est ni confirmé ni infirmé sans ce fichier.



\### Preuve 3 — conso.js a son propre système de persistance, complet et autonome



```javascript

// conso.js ligne 35

this.storageKey = "claraverse\_tables\_data";   // ⚠️ clé UNIQUE et GLOBALE



// conso.js ligne 53 (au démarrage du script, indépendant de React)

```



`conso.js` sauvegarde et restaure \*\*lui-même\*\*, via `localStorage`, sans jamais passer par `flowiseTableBridge` ni IndexedDB. `restoreAllTablesData()` est appelée automatiquement 1500 ms après l'initialisation du script (ligne 2332+), indépendamment du cycle de vie React. \*\*Donc l'absence de `useEffect` dans ClaraAssistant.tsx n'explique pas la perte de Table\_Conso / Resultat / Modelised\_table\*\* — ces tables ont leur propre mécanisme de restauration qui tourne déjà.



\### Preuve 4 — 🔴 LE VRAI PROBLÈME : ni sessionId, ni ID stable par contenu




```bash

$ grep -n "sessionId\\|currentSession" conso.js

(aucun résultat)
```

\*\*`conso.js` ne connaît absolument pas la notion de session/chat.\*\* L'ID d'une table est un simple hash de ses en-têtes de colonnes (`Assertion`, `Conclusion`, `Ctr1`, `Ecart`...). Or, d'après le doc métier (03), \*\*les 71 feuilles de test partagent exactement les mêmes 11 types de tables avec les mêmes en-têtes\*\* (Modelised\_table Caisse et Modelised\_table Immobilisations ont des colonnes identiques).



\*\*Conséquence directe et vérifiée par le code — pas une hypothèse :\*\*

\- Toutes les `Modelised\_table` de tous les chats génèrent \*\*le même `tableId`\*\* (car mêmes en-têtes).

\- La clé `localStorage\["claraverse\_tables\_data"]` est \*\*globale à toute l'application\*\*, pas par session.

\- Résultat : la dernière feuille de test remplie \*\*écrase silencieusement\*\* les données de toutes les autres feuilles de test partageant les mêmes en-têtes, ET `restoreAllTablesData()` réinjecte au F5 des données qui peuvent appartenir à \*\*n'importe quel autre chat\*\*.



Ceci explique \*\*simultanément\*\* les deux symptômes rapportés par l'utilisateur métier dans le doc 03 :

1\. \*« Les modifications ne sont pas persistantes après F5 »\* → écrasement inter-sessions du même slot `localStorage`.

2\. \*« Un mélange des 11 types de tables d'un autre chat apparaît »\* → restauration globale sans filtre de session, avec collision d'ID par en-têtes identiques.

\## 2. HYPOTHÈSES DE SOLUTION



\### Solution S1 (prioritaire) — Scoper la clé de stockage par session dans conso.js



Remplacer la clé globale unique par une clé dérivée du `sessionId` du chat courant.



```javascript

// AVANT

this.storageKey = "claraverse\_tables\_data";



// APRÈS

getStorageKey() {

&#x20; const sessionId = this.detectCurrentSessionId(); // à implémenter, voir S3

&#x20; return sessionId ? `claraverse\_tables\_data\_${sessionId}` : "claraverse\_tables\_data\_unsaved";

}

```

Tous les appels à `loadAllData()` / `saveAllData()` doivent utiliser `this.getStorageKey()` au lieu de `this.storageKey` figé.



\*\*Effet attendu\*\* : chaque chat a son propre "tiroir" localStorage → fin de la contamination et de l'écrasement inter-sessions.



\### Solution S2 (prioritaire) — Inclure le sessionId dans le calcul du tableId



```javascript

// generateUniqueTableId(table)

const sessionId = this.detectCurrentSessionId();

const headerText = headers.map(...).join("\_\_");

const hash = this.hashCode(`${sessionId}::${headerText}`); // sessionId injecté dans le hash

```



\*\*Effet attendu\*\* : deux `Modelised\_table` de deux chats différents obtiennent désormais des ID distincts même avec des en-têtes identiques.



\### Solution S3 (prérequis technique de S1/S2) — Détection fiable du sessionId depuis conso.js



`conso.js` est un script injecté globalement (pas un composant React), il doit donc lire le `sessionId` depuis le DOM, exactement comme le fait déjà `flowiseTableBridge.detectSessionId()` (ligne \~450 du fichier bridge, méthode déjà éprouvée). Réutiliser la même stratégie en cascade :

1\. `document.querySelector('\[data-session-id]')`

2\. `document.querySelector('\[data-chat-session-id]')`

3\. Écoute de l'événement `claraverse:session:changed` déjà dispatché ailleurs dans l'app (le Bridge l'écoute déjà, donc l'événement existe) pour maintenir une variable `this.currentSessionId` à jour dans `conso.js`, plutôt que de re-scanner le DOM à chaque sauvegarde.



\*\*Point d'attention\*\* : si le `sessionId` détecté est temporaire/instable (cf. doc 02, section `detectSessionId`), S1/S2 échoueront aussi. Il faut valider la stabilité du sessionId \*\*avant\*\* d'implémenter S1/S2 (voir Phase 0 ci-dessous).



\### Solution S4 — Filtrer la restauration par les tables réellement présentes dans le DOM courant



`restoreAllTablesData()` (ligne 2332) restaure déjà uniquement les tables trouvées par `findAllTables()` dans le DOM courant — donc une fois S1/S2 appliquées, une table d'un autre chat n'aura de toute façon plus la même clé de stockage à lire. S1/S2 rendent S4 non nécessaire en soi, mais on peut ajouter une double vérification (defense in depth) : comparer `data-session-id` de la table restaurée au `sessionId` courant avant injection.



\### Solution S5 (secondaire, système Flowise/IndexedDB) — Vérifier puis corriger ClaraAssistant.tsx



Indépendamment de S1-S4, il reste légitime de vérifier si `restoreTablesChronologically()` est bien appelé pour les \*\*8 autres tables\*\* (Table\_entete, Table\_objectif, etc., généralement en lecture seule, générées par le LLM et non par conso.js). Le correctif proposé dans les docs 02/03 reste valable pour \*\*ce sous-système uniquement\*\* :



```typescript

import flowiseTableBridge from '../services/flowiseTableBridge';



useEffect(() => {

&#x20; if (!currentSession?.id || !messages || messages.length === 0) return;

&#x20; flowiseTableBridge.restoreTablesChronologically(messages)

&#x20;   .then(count => console.log(`✅ ${count} table(s) restaurée(s)`))

&#x20;   .catch(err => console.error('❌ Erreur restauration:', err));

}, \[currentSession?.id]); // dépendance sur l'ID seul, pas sur "messages" en entier (évite déclenchements répétés à chaque nouveau message, cf. Q1 doc 02)

```



⚠️ Ne pas mettre `messages` (le tableau) en dépendance de `useEffect` — sa référence change à chaque nouveau message, ce qui redéclencherait la restauration en boucle. Utiliser `messages.length` ou un `useRef` guard comme évoqué dans le doc 02 (Option B).

\## 3. PLAN D'IMPLÉMENTATION



\### Phase 0 — Vérification préalable (10-15 min, obligatoire avant tout code)



Ne pas coder S1/S2 avant d'avoir confirmé ces 3 points, sinon on répare un mauvais tiroir avec une mauvaise clé :



1\. \*\*Confirmer la collision d'ID\*\* : ouvrir deux chats différents ("Test Caisse", "Test Trésorerie"), générer une `Modelised\_table` dans chacun, puis dans la console :

&#x20;  ```javascript

&#x20;  document.querySelectorAll('\[data-table-id]').forEach(t =>

&#x20;    console.log(t.dataset.tableId, t.closest('\[data-session-id]')?.dataset.sessionId)

&#x20;  );

&#x20;  ```

&#x20;  Si les deux tables affichent le même `tableId` → \*\*H1/H2 confirmées\*\*.

2\. \*\*Confirmer le contenu de `localStorage`\*\* : `JSON.parse(localStorage.getItem('claraverse\_tables\_data'))` — vérifier qu'une seule entrée existe par hash de en-têtes, partagée entre chats.

3\. \*\*Confirmer la stabilité du sessionId\*\* détecté dans le DOM (`\[data-session-id]` présent et stable entre deux rendus) — sinon S3 doit d'abord router ce problème (cf. doc 02, section `detectSessionId`, risque de sessionId temporaire régénéré à chaque appel).



\### Phase 1 — Correctif conso.js (30-40 min)



1\. Ajouter `currentSessionId` + méthode de détection (S3) dans `ClaraverseTableProcessor`, avec écoute de `claraverse:session:changed`.

2\. Remplacer `this.storageKey` fixe par `getStorageKey()` dynamique (S1) partout où `loadAllData()`/`saveAllData()` sont appelés (≈10 sites d'appel recensés : lignes 77, 2142, 2208, 2230, 2248, 2266, 2335, 2456, 2485, 2500, 3388, 3564, 3582, 3664).

3\. Injecter le `sessionId` dans `generateUniqueTableId()` (S2).

4\. Ajouter un log explicite de la clé de stockage utilisée à chaque sauvegarde/restauration pour validation (`console.log('💾 \[conso.js] Storage key:', this.getStorageKey())`).



\### Phase 2 — Migration des données existantes (10 min)



Les données déjà présentes sous l'ancienne clé globale `claraverse\_tables\_data` seront orphelines après la Phase 1. Prévoir soit :

\- Un script de migration one-shot qui, au premier chargement post-déploiement, relit l'ancienne clé et tente de la répartir par `sessionId` si l'information est reconstructible (peu probable, car l'ancien format ne stocke pas le sessionId) ;

\- Soit, plus réaliste : accepter la perte de cet historique ancien et informer les utilisateurs (l'app étant en développement actif, cf. doc 03).



\### Phase 3 — Vérification/correctif ClaraAssistant.tsx (système secondaire, 15-20 min)



Appliquer S5 seulement après la Phase 0, en confirmant d'abord par `grep` que le fichier ne contient effectivement aucun appel à `restoreTablesChronologically`. Ce correctif n'affecte que les tables du système Flowise/IndexedDB (probablement les 8 tables non modifiables).

\## 4. RISQUES ET PRÉCAUTIONS



\- \*\*Ne pas toucher\*\* au filtrage `sessionId` déjà en place dans `flowiseTableBridge.ts` (ligne \~2324) — il fonctionne correctement et sert de modèle pour S3.

\- \*\*Risque de sessionId instable\*\* : si `detectSessionId()` bascule sur un ID temporaire à chaque appel (cas déjà documenté dans le doc 02), S1/S2 ne corrigeront rien — à valider en Phase 0 avant de coder.

\- \*\*Perte de données historiques\*\* lors de la migration de clé (Phase 2) — à communiquer clairement, l'app étant encore en développement selon le contexte fourni.

\- \*\*Ne pas réimplémenter l'anti-doublons\*\* supprimé précédemment (cf. contrainte du doc 03) tant que la Phase 1 n'est pas validée en production.

\- \*\*Vérifier que `index.html`\*\* (non fourni dans cette analyse) ne contient pas déjà une logique de pont `claraverse:\* → flowise:\*` qui invaliderait H3 — demander ce fichier avant implémentation si le doute persiste.
