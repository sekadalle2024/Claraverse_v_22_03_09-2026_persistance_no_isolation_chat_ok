C'est un artefact de la minification d'esbuild :



1\.  Les variables comme EXCLUDED\_KEYWORDS sont renommées en une seule lettre

&#x20;   "..." + t + "". Ton grep strict échoue, te faisant croire (à tort) que le

&#x20;   code a été "tree-shaké".

4️⃣ MÉMO DE RÉSOLUTION (Pour ton équipe / Git)



\# RÉSOLUTION FINALE - Bug de Persistance Tables de Consolidation



\## Problème

Les tables `Table\_Consolidation` et `Resultat` étaient sauvegardées en IndexedDB et restaurées dans d'autres sessions, causant une contamination. Le code de blocage initial semblait ignoré par le build.



\## Root Cause

1\. \*\*Bypass Logique :\*\* Le blocage initial était placé dans `handleTableIntegrated`, mais les tables de consolidation sont sauvegardées via `conso.js` qui émet `flowise:table:save:request`, déclenchant `handleTableSaveRequest`. Le blocage était donc contourné.

2\. \*\*Illusion de Tree-shaking :\*\* Le code n'était pas supprimé par Vite, mais minifié (variables renommées), rendant les recherches `grep` infructueuses.



\## Solution Implémentée (Défense en Profondeur 3-Layers)

1\. \*\*Layer 1 (DOM) :\*\* Interception globale des événements en phase de capture dans `index.html` pour tuer la requête à la source.

2\. \*\*Layer 2 (Service) :\*\* Blocage strict dans `flowiseTableService.saveGeneratedTable` (point de passage unique vers IndexedDB).

3\. \*\*Layer 3 (Bridge) :\*\* Filtrage des tables exclues lors de la restauration (`restoreTablesForSession`) pour ignorer les anciennes tables corrompues en base.



\## Commits Git Suggérés

\- `fix(persistance): implement 3-layer defense against table contamination`

\- `perf(dom): intercept excluded table save events at capture phase`

\- `chore(db): add failsafe in IndexedDB service to block excluded keywords`



Avec cette architecture, il est techniquement impossible qu'une table de

consolidation finisse dans la base de données ou soit restaurée. Ton problème de

contamination est définitivement réglé ! 🚀
